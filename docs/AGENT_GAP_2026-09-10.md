# The gap read from the agent's side — where intelligence is spent, 2026-09-10

Written after V31 Phase 2 (half) (`852ddf6`). The V30 architecture note
(`ARCHITECTURE_AND_TESTING_2026-09-09.md`) reads the desk by layer and by role, from summary counters.
This one reads the same desk from inside one turn: what the model was handed, what it sent back, and
what the desk said to it — because a counter that says "2.70 respond attempts" does not say whether the
model was wrong twice or right once and refused twice for how it said so.

**Evidence.** The step-level traces of the V30 rounds (C1–C3) are not committed; only their counters
are. The traces that ARE committed are `docs/spikes/v29/V26_R2.json` — 140 turns, the baseline pinned at
`e6c290b`, which is the code running in production. So every trace quoted below is the LIVE agent, not
the branch. Where the branch differs, it is said. The V30 C3 refusal census (`v30/PHASE0.md`) and
`tests/battery/gold_brief.json` (committed 852ddf6) fill in what the branch changed.

---

## 0. The result in one paragraph

Half of what the answer gate refuses is not a wrong figure; it is a right answer said in the wrong
grammar. On the 140 committed baseline turns, `respond` is called 284 times and refused 143 — and 134
of those 143 (94%) are refusals about how a number or an id was written, not about whether it was true.
The model's own errors are two: it re-sends an unchanged payload after a refusal, and it re-words a
superlative rather than computing a rank. Both are amplified by the desk — the first because a refusal
says what the rule is and never which token broke it, the second because "compute the ordering first"
is a sentence in a prompt rather than a shape in a tool. Underneath that, two structural losses: a
batch holds back calls the model got right because an earlier call in the same batch was wrong (41
occurrences), and the skill's knowledge sits behind a second `describe` call the model makes 3 times in
140 turns.

## 3. Is the agent's intelligence limited — yes, in three ways, each owned by a different role

**validation — the gate defines the language the model must speak, and does not say where it broke.**
94% of refusals are about saying. Three loops in 140 turns end with a right answer discarded. The
refusal carries the rule and not the token: `gate._FIX` is `PROSE_RULE` plus one imperative, and
`problems[].figure` holds the offending token but the model is handed the class, not the instance.

**tool — failure is closed over the batch and over the call.** `agents/batch.py:74` holds every later
call in a batch behind an earlier one's error: 41 held calls in 140 turns, all of them calls the model
addressed correctly. `fact_adapters._unit_for` (line 180) raises `UnknownUnit` when a numeric key is in
no table, and the wrapper discards every figure in that result — three occurrences in 191 turns, still
unfixed anywhere (`quality_flags`/`unmatched_periods` are in none of the five key tables).

**skill — the knowledge is on a pull channel nobody pulls.** `ROOT_CAUSES.md` §1e measured it: domain
cards opened 3 times in 140 turns; 22% of turns reach any method their own domain names. And the
knowledge that exists is not applied where the programs are built: `gold_brief.json` gives JPM 18
`not_applicable` refusals (DSO, inventory days, CCC on a bank) plus 10 `depends_on_refused` — 28 of its
32 — while `not_for_financials` is recorded in three other places (`analytics/skill.py:99`,
`catalogue_service.py:278`, the formula registry).

**LLM — two real ones.** Re-sending an unchanged payload after a refusal (2.1, 2.3). And re-wording a
superlative instead of computing an ordering: `superlatives_without_rank` reads 37 / 36 / 37 across
both baselines and V30 — neither protocol moved it.

The growth pattern is the thing to name: **each version fixes the previous version's refusal with a new
refusal.** `SPELLING_REFUSALS` was added, over-reached, and was narrowed; an `absent` claim had no
address for a desk policy, so an address was added; `nearest` answered a wrong method name with a real
method that is the wrong figure (`revenue`→`roe`), so `wrong_door` routing was added. Each step is
right. The sum is thirty ways to be refused.

That this is not inherent: V29 made `compute`'s `method` a schema enum and `unknown_method` went 32 → 0
by construction. V30 moved method names back inside the program JSON where nothing binds them, and
`METHOD_NAME_REPLAY.md` records the honest position — zero occurrences is *unverified*, not *safe*.

**A contradiction the model reads today.** `meta_agent._SYSTEM` says *"Figures come from ONE tool:
run(program)"*, and 31 refusal strings in src still tell the model to call `read_fundamentals(…)`,
`read_prices(…)` or `compute(method=…)` — three tools that are on neither face since 852ddf6. `start`'s
description still routes a hypothetical trade to `compute(method='book.sell')`. The advice a model
reads at the moment it is refused points at a tool it cannot call.

## 6. The root, and the order to fix it

**One decision, projected into three layers: "validation ensures correctness" was built as "validation
defines the language". ** The agent's intelligence is then spent on the grammar; the tool layer fails
closed over a batch and over a call, so correct work is discarded; and the skill's knowledge sits on a
pull channel behind a second call.

By return on effort:

1. **A refusal names WHERE, and an unchanged resubmission short-circuits.** Token- and claim-level
   location plus one remedy; a byte-identical payload refused twice returns the previous refusal
   without spending a provider call. The 8-attempt loops end.
2. **An answer with no figures does not go through the figure gate.** "Fixed or floating" needs a
   quote/citation exit.
3. **Push instead of pull.** `describe(ticker)` carries its domains' evidence and what is
   `not_applicable` for this issuer kind; the skill filters its programs at generation. The 3/140
   domain-open rate and JPM's 18 are one problem.
4. **A batch does not fail closed, and an unknown key fails on the key.** 41 held calls plus §4.2.
5. **Delete the 31 refusal strings that route to retired tools.**

### What this commit does

**1, 4 and 5** — the three that are local, and that the offline suite can verify. 2 and 3 are contract
changes (a new exit on the gate; the catalogue's model-facing shape) and belong with the boss's read of
the model-facing wording, per the standing rule.

One correction to §6.1 as first written, found in the code rather than in the traces: **the refusal
already names where.** V30's claims gate returns `problems` with `at` (which paragraph or claim) and
the offending `figure` / `id` / `relation` beside the reason — `claims.check` builds them, and
`as_refusal()` sends them. It is the OLD gate (`gate._FIX`, the brief path before Phase 2, and the
`e6c290b` the traces come from) that hands over the rule and nothing else. So on this branch the model
is already told the token; what the three eight-attempt turns show is that a model which re-sends
byte-identical prose is not reading it. The half of item 1 that is real work is therefore the
short-circuit, and that is what is built:

| built | file | what it does |
|---|---|---|
| 1 | `agents/repeats.py`, wired into both loops | a refused exit re-sent unchanged is told so once, with the tokens the gate named, and ends the turn on the second repeat. Nothing the gate refused is published; an exhausted turn ends on the same text, having spent three submissions instead of eight. A payload that CHANGED is never held |
| 4a | `agents/batch.py` | `invalid_params` / `invalid_arguments` hold only a call that repeats those arguments. V21-S1's class (ten calls composed under one wrong belief about a NAME) stays closed, and V23's `held_on` still wins |
| 4b | `services/fact_adapters.py` | a numeric leaf with no declarable unit is marked `untyped:<key>` and named in the note; it is never a Fact and never a bare number (I1 holds), and every figure that DID type survives. `quality_flags` joins `PASSTHROUGH_KEYS`, the contract `typed_calculator._is_single_valued` has stated since V29. The producer's missing declaration is still loud — in the desk's log, where loudness costs nothing |
| 5 | 7 modules, 14 strings | every refusal on the run path speaks the program language. Guarded: `test_no_refusal_on_the_run_path_routes_the_model_to_a_retired_tool` walks every string constant under `src/` |

## 7. A and C, built (2026-09-10, second commit)

### A — the refusal routes instead of only refusing

`unsourced_figure` is the commonest refusal this desk issues (69 of 143 on the V26 baseline), and the
commonest shape behind it is a number the session **has** retrieved, sitting in a passage no `quote`
claim cites. Only cited passages are searched for acceptance, and that restriction stays exactly as it
is — `ledger.py` records why: the 2026-09-05 round linked an invented "low-20s percent" to a 10-K that
happened to contain the digits 20.

What changed is what the model is told. `claims._where_it_lives` re-runs `resolve_in_passages` over the
passages the session holds but did **not** cite, and when it hits, the refusal names the chunk and the
fix — on `problems`, and on the top-level `detail`, which is the line a model demonstrably does read
(three turns re-sent unchanged prose eight times each while `problems` already named the token).

Because the hint uses the acceptance function itself, it is exactly as precise as acceptance: a bare
short integer never matches, so a hint is never offered where accepting would have manufactured a
source. Pinned by four tests, including that one.

### C1 — `reading_holds`

Every criterion this desk had scored sourcing, coverage or form: `grounded_claims` asks where a figure
came from, `honest_absence` what was said about a missing one, `precision` how it was written, `so_what`
whether the answer closed on something actionable — a presence check, not a correctness one. Nothing
asked whether the **reading** is right. That is why V30 could halve the cost of a turn and report
correctness "a dead heat": the instrument cannot see the thing.

The new criterion is deliberately bounded to what an answer can be judged on without re-deriving the
finance — *internal entailment*. The judge is not asked whether ExxonMobil's debt really is fixed-rate;
it is asked whether the sentence follows from the figures printed beside it.

It applies to every answered turn (a question does not have to ASK for a sound reading for an unsound
one to be a defect) and is reported on **its own line, outside `TOTAL`**. Folding a universally-applied
criterion into the totals would move every score line on unchanged code, and this desk has already
withdrawn one conclusion that was replicate noise; a second that was a denominator change would be
worse.

**Cost, stated before it is spent:** on v26 the semantic pass goes from 466 to **606 judge calls,
~297k prompt tokens per replicate**. Not run — the account has no credit. C1 ships as an instrument
with no reading.

### C2 — a number off its basis, deterministic

`figures_present` asks whether the gold value appeared. It is structurally blind to the number printed
*in its place* — and a figure that is nearly right is worse for a reader than one that is absent. The
detector looks for a rendered figure that is a gold figure times a basis this desk has actually
confused: ×365/90 (a days measure on a quarter grid — PHASE0 defect 1, `days_inventory` at 424–479),
×4 (a quarter against the trailing twelve months), ×100 (V29: a $1,135,470 spread shown as
"113547000.0%"), ×1000.

**The build is the finding.** Measured on V26_R2 while writing it:

| constraint | hits | what they were |
|---|---|---|
| value ratio only | **637** | all coincidence — ~700 gold figures × ~20 rendered per turn, some pair lands on a ratio. `limit_checks.breach_level = 0.03` was flagged because a weight in gold is 0.01 |
| + same subject, same unit | **5** | still all coincidence: `issuer_exposures.daily_return` against `holdings.window_return`, `contribution ÷ weight` against `contribution` — real figures, different quantities, a round multiple apart |
| + same measure **name** | **0** | — |

The name is what makes a hit mean anything, and needing it is the same Class 1 the rest of this
codebase has: gold says `holdings.window_return` in its `note`, a rendered figure says it in `label`,
and where those two vocabularies do not meet the detector is blind.

Run across the four committed rounds — V26_R1, V26_R2, V21_R1, V24_R1 — it reports **0**. That is a
bound and not a clearance: it is `METHOD_NAME_REPLAY`'s rule again, zero occurrences is *unverified*,
not *safe*. So the teeth are pinned separately: a unit test reconstructs both documented defects
(`days_inventory` at 429.9 against a gold 106; the spread at 113,547,000 against a gold 1,135,470) and
asserts the detector names each one, and a fourth asserts the `daily_return`/`window_return` pair that
survived the looser constraint is **not** reported.

Offline suite **2273 passed**.

### Found on the way: the brief battery does not compile on the Python this project declares

`scripts/brief_battery.py` — the instrument V31 Phase 2 (half) exists to build — puts an implicit string
concatenation inside an f-string replacement field. That is PEP 701, Python 3.12; `pyproject` declares
`requires-python = ">=3.11"`. On 3.11 the script raises `SyntaxError` at import and never reaches its
first line.

It predates this work (it is in `852ddf6` as committed) and nothing caught it because the offline suite
never imports `scripts/`: 2,254 tests were green over a script that could not start. That is V28-R's
shape one layer down — green tests over a thing nobody executed, which is the failure the preflight in
that same file was written to prevent.

Fixed by hoisting the conditional out of the f-string, and guarded:
`test_every_script_compiles_on_the_declared_minimum_python` compiles every file under `scripts/`.

## 8. 2 and 3, built (2026-09-10, third commit)

### 2 — first, the premise was wrong, and the correction is the finding

§6 listed *"an answer with no figures does not go through the figure gate"* as a contract change worth
making. Probed against the branch before building it, it turns out **the exit already exists**:

| an answer that is… | verdict today |
|---|---|
| prose with no digits at all, no claims | **accepted** |
| prose with a digit from a filing, no quote claim | refused `unsourced_figure` — and since A, routed |
| the same digit with a `quote` claim citing the passage | **accepted** |

So there was nothing to build. W01-xom-maturity-wall was never blocked by a missing exit; it was blocked
by not knowing it had to file a `quote` claim to open the one that exists — which is what A now tells it.

What the probe DID find is the same defect one refusal over. `verify_quotes` is handed
`[led.passages[p] for p in cited_passages]` — the quote-claim-cited passages, and nothing else. A model
that ran `read_filings`, read the words and reproduced them **exactly** is told its quotation is
unverified, while the passage it copied them from sits on the same ledger, uncited. That is
`unsourced_figure`'s class on `unverified_quote`, the second commonest refusal this desk issues: **31 of
the 143** the V26 baseline collected, behind `unsourced_figure`'s 69.

`claims._where_the_words_live` routes it, the same way and under the same rule — acceptance unmoved, the
chunk named on `problems` and on `detail`. It needs no precision guard of its own: a quoted span is
already four words or more (`gate._MIN_QUOTED_WORDS`), and a four-word verbatim match is not something a
filing produces by accident. It reads the words through `gate._normalise`, the function `verify_quotes`
itself uses, so curly quotes, dashes and case cannot make the check and the hint disagree.

### 3 — the domain says which of its own methods refuse here

Two halves of §6.3, and only one of them was still missing.

**Already fixed, before this session.** ROOT_CAUSES §1e measured that a domain's methods were behind
`expand=<domain>` — but V27's directory put `methods` and `reads` on the level-1 entry. That half is
done; the 3/140 domain-open rate was measured on a payload that no longer exists.

**Still missing.** Whether those methods work *for this issuer*. The reasons existed — the issuer view
carries `fundamentals.methods_not_computable` with `"not for a financial issuer"` — in a **different
section of the same payload**, so a model reading a domain had to cross-reference to learn that the
domain it was about to work through does not apply. It did not, and neither did the desk: the desk's own
seven issuer domains run over JPM produce 50 figures and **32 refusals, 18 of them `not_applicable`** —
days sales outstanding, days inventory and the cash conversion cycle asked of a bank
(`tests/battery/gold_brief.json`).

A domain entry now carries `methods_that_refuse_here: {method: why}`. For JPM:

| domain | methods | refuse here |
|---|---|---|
| `issuer_credit_and_balance_sheet` | 9 | **9** |
| `issuer_profitability` | 10 | 4 |
| `issuer_earnings_quality` | 6 | 4 |
| `issuer_capital_allocation` | 3 | 3 |
| `issuer_business_risk_from_filings` | 3 | 2 |
| `issuer_price_context` | 5 | 0 |

The payload grows only where there is something to say — the rule `lines` already follows — so an issuer
whose filings feed everything gains no key at all.

And the rule got one home on the way. `_computability` was inline in `_fundamentals`, which is why the
issuer view and the domain view could have disagreed about the same issuer; both read it now, and a test
asserts `"not for a financial issuer"` occurs exactly once in the module. A domain listed for an issuer
and that domain **opened** for that issuer are one statement or they are a defect.

## 11. The three C3 classes, read as the model's input and output (2026-09-10, late)

§10 named three limits. This section asks, for each, exactly what the model was handed and what it sent

### The input, in full, at the moment a claim is written

## 12. The root cause, stated once (2026-09-10)

Not "which example broke". Which component did not do its job, and whether that is for want of input or
because the function is designed wrong.

### It is not for want of input. In every case the knowledge was already in the system.

| the decision | who made it | who already knew | was fixed |
|---|---|---|---|
| what unit a number carries | `fact_adapters._unit_for`, by looking the key up in a table | `program_service._facts_of` — the producer types every node at birth | yes (4b) |
| how far a refusal reaches | `batch.holds`, by tool name | the refusal itself — an argument error is about its arguments | yes (4a) |
| whether a domain's methods apply to this issuer | nothing, in the domain view | `catalogue_service` line 279, in the fundamentals section of the same payload | yes (item 3) |
| **which check an answer gets** | **`claims._check_relation`, by dispatching on `c["relation"]`** | **the facts — same measure, same period, same value is a fact about the facts** | **no** |

The first three are one mistake in three places: **the decision was made one layer away from the
knowledge, so the decider had to infer what the producer had declared.** All three are closed.

The fourth is a different mistake, and it is the live one.

### The design error: the party under validation chooses which validation runs

`_check_relation` switches on `relation`, and `relation` is a field the model writes. Run on the branch,
same two facts, same sentence:

```
two facts: limit_checks.issuer_concentration:MSFT.current_value, both 2026-09-04, both 0.08757…
prose:     "…leaves concentration at {c1}, down from {c2}."

declared as one  change  -> REFUSED   (different_measures)
declared as two  levels  -> ACCEPTED
```

Nothing else changed. Choosing the weaker relation is a legal move that removes the check, and it is
what produced C3's one self-contradicting accepted answer (§10). The gate contains **zero** occurrences
of "down", "rose", "higher", "largest" — it never reads what the sentence asserts, so it cannot notice
that the declaration and the sentence disagree.

The same shape explains the superlative (§11): a `rank` claim invites `no_ordering`; a superlative in
prose invites nothing. **The model is not evading the gate — it is choosing, correctly, among moves the
gate offers.**

### The second design error: the unit of validation is not the unit of meaning

`_check_relation(c, led)` takes **one claim**, and `check` runs it `for c in answer["claims"]`
independently. No function in the module takes the claim set. The reader reads a sentence; the gate
validates pointers, one at a time. Two claims that are individually perfect and jointly absurd is
outside what any signature can express.

### The desk has already written this down, and drawn the opposite conclusion for the report

`numeric_verification` names the class exactly: *"The citation gate proves an id is real. It says
nothing about the NUMBER standing next to it, and 'right citation, wrong number' is the failure a
finance desk cares about most."* It is the v1 path, serving the daily report and an offline eval; it is
not on the chat exit.

`report_verification` says why the report can be stricter: *"`respond` and `submit_brief` verify against
evidence the agent chose… A report has no choice to state… the evidence set is assembled HERE… The brief
gate can only ask 'does this number appear in something you cited' — an existence check against a
corpus. This one asks 'is this number a value of a row of this run'."*

Read together with the run above, that is the architecture in one line: **this desk's validation is
strong exactly where the model chooses nothing, and weak exactly where the model chooses the frame.**
The report gate assembles its own evidence and checks values. The chat gate takes the model's evidence
AND the model's choice of relation, and checks existence.

### So: whose function has not been executed

**Validation's.** Not for want of input — it holds the facts, their measures, periods, values and the
placeholder positions, which is everything the W05 case needs. Two design faults, both structural:

1. **the dispatch key is written by the party being checked** — a relation should be *derived* from the
   facts a claim points at and *verified* against the claim, not accepted as the instruction for which
   verification to run;
2. **the predicate is never represented** — the typed half of an answer carries pointers, the assertion
   lives in untyped prose, and nothing spans a sentence.

Everything else did its job or has been fixed. The tool layer's three faults were placement, all closed.
The LLM's behaviour under this gate is rational: in W01 it answered correctly at the first attempt; in
W01-stop-sweep t2 it computed the whole vector an ordering needs and then stated the ordering where
nothing would test it.

### What follows (not built, no round behind it)

- derive the relation from the facts and check the model's declaration against it, rather than
  dispatching on it;
- give the gate one function whose argument is the claims of one paragraph, so "same measure, same
  period, same value, adjacent in one sentence" is expressible at all;
- `reading_holds` (C1) remains the only thing built that points at the predicate, and it has never run.

## 13. §12 corrected, from the source rather than the spikes (2026-09-10)

§12's first recommendation — *derive the relation from the facts instead of dispatching on it* — is
**wrong**, and the source says so. Run on the branch, one fact, three declarations:

```
issuer_exposures.weight  MSFT  RATIO  0.161  params {node: w, label: MSFT, rank: 1}

   declared level -> ACCEPT      (a scalar that is not a tier)
   declared rank  -> ACCEPT      (params carries rank)
   declared ratio -> ACCEPT      (unit is RATIO)
```

One fact, three legal relations. The relation is **not** a function of the facts, so it cannot be
derived. It is not redundant machinery: `level` says *"MSFT is 16.1%"*, `rank` says *"MSFT is the
largest"*, `ratio` says *"MSFT is 16.1% OF the book"* — three different sentences about one number.
**The relation is the only typed fragment of the model's assertion this grammar has.**

That reframes §12's whole diagnosis. The fault is not that the model picks the check. It is what the
grammar can express at all.

### What the answer grammar can and cannot say

`ANSWER_SCHEMA` gives a claim exactly `{id, relation, of, against, rows, span, title}`. **Arity two**:
one fact in `of`, at most one more in `against`. Eleven relations, of which exactly three
(`change`, `versus`, `room`) relate two facts, and each has a one-place alternative the model may
declare instead. `table` takes many ids but is a grid, not an assertion.

Beside it, the program language the same model writes: `sub(a,b)`, `div(a,b)`, `sum(of)`, `avg(of)`,
`rank(of)`, `top(of, n)` — nested, over vectors, unbounded. **The analysis half is compositional; the
assertion half is a flat list of pointers, each carrying one one-place tag.**

So an ordering over ten holdings is expressible as a program node and **inexpressible as a claim** —
the answer can only point at one entry of it. The predicate that has no shape goes where there is
room: the prose. That is the superlative (§11), and it is not a choice the model made badly.

### The W05 contradiction, and what the gate already computes

Two facts, same measure, same period, same value, adjacent in one sentence, declared as two `level`s:
**accepted**. Every field a check would need is on the two records, and the fourth — *are these two
claims in the same sentence* — is already computed: `validate_shape` walks `PLACEHOLDER` per paragraph
to validate the ids, then returns only its problem list and drops the mapping.

`_check_relation(c, led)` takes one claim; `check` runs it `for c in answer["claims"]` independently.
No function in the module has more than one claim in scope. Two claims individually valid and jointly
absurd is not something any signature there can express.

### The root cause, restated

**Validation's function is designed wrong, and the design fault is expressive, not procedural.** Not
for want of input — the facts, their measures, periods, values and the sentence they share are all in
hand.

1. **The assertion is typed at arity one; the analysis is composed at arity many.** A claim can say what
   one fact *is*. It cannot say what several facts are *to each other* except in three special cases,
   each of which the model may decline by declaring one-place claims instead.
2. **The gate's unit is a claim; the reader's unit is a sentence.** The paragraph→claims mapping exists
   for one line and is thrown away.

`numeric_verification`'s own words — *"the citation gate proves an id is real; it says nothing about the
NUMBER standing next to it"* — name the consequence. `report_verification`'s — *"the brief gate can only
ask 'does this number appear in something you cited'"* — name the shape. Both are in the source, and
neither is on the chat exit.

### What actually follows

Not "derive the relation" — that is refuted above. Two things the source supports:

- **give the assertion the arity the analysis already has**: a claim whose `of` is a node (an ordering,
  a set) rather than one entry, so a superlative is sayable and therefore checkable;
- **give the gate one function whose argument is the claims of one paragraph**, using the mapping
  `validate_shape` already builds — enough, on its own, for "same measure, same period, same value,
  one sentence".

Neither is built. `reading_holds` (C1) remains the only thing that points at the predicate, and it has
never run.
